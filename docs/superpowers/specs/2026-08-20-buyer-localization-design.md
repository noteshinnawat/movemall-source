# การออกแบบระบบหลายภาษาสำหรับหน้าผู้ซื้อ

วันที่: 20 สิงหาคม 2026  
สถานะ: อนุมัติแนวทางและขอบเขตแล้ว รอตรวจทานเอกสารก่อนจัดทำแผนลงมือแก้ไข

## 1. เป้าหมาย

เพิ่มการรองรับภาษาไทย อังกฤษ และพม่าให้ส่วนติดต่อผู้ซื้อของ Movemall โดยเมื่อผู้ใช้เลือกภาษาใด ข้อความของระบบต้องแสดงเฉพาะภาษานั้น ไม่มีคำแปลภาษาอังกฤษกำกับข้อความภาษาไทย และไม่เปลี่ยนภาษาของเนื้อหาที่ร้านค้าหรือผู้ใช้เป็นผู้สร้าง

รหัสภาษาที่ใช้ในระบบมีดังนี้:

| ภาษา | รหัส | ชื่อที่แสดงในเมนู |
|---|---|---|
| ไทย | `th` | ไทย |
| อังกฤษ | `en` | English |
| พม่า | `my` | မြန်မာ |

ภาษาไทยเป็นภาษาเริ่มต้นและเป็นภาษาสำรองเมื่อคำแปลของภาษาอื่นขาดหาย

## 2. ขอบเขตระยะแรก

### 2.1 ส่วนที่รวม

- ส่วนกลางของหน้าผู้ซื้อ: Navbar, Footer, Mobile Bottom Nav, Toast, Error Boundary, Cookie Consent, PWA Install Prompt, Visual Search Modal, Live Activity Ticker และ Floating Live Widget
- การเลือกดูสินค้า: หน้าแรก ร้านค้า Mall รายการสินค้า รายละเอียดสินค้า รายการร้านค้า และหน้าร้านค้า
- ความบันเทิงและโปรโมชัน: ไลฟ์ วิดีโอ เกม Flash Sale และคูปอง
- ธุรกรรมผู้ซื้อ: ตะกร้า ชำระเงิน ผลการสั่งซื้อ ประวัติคำสั่งซื้อ รายการโปรด และเปรียบเทียบสินค้า
- บัญชีผู้ซื้อ: เข้าสู่ระบบ สมัครสมาชิก บัญชีผู้ใช้ แชต การแจ้งเตือน และติดตามพัสดุ
- เนื้อหาสาธารณะ: ศูนย์ช่วยเหลือ นโยบายความเป็นส่วนตัว และข้อกำหนดการใช้งาน
- SEO, ข้อมูลกำกับหน้า, PWA manifest และคุณลักษณะช่วยการเข้าถึงที่ผู้ใช้มองเห็นหรือโปรแกรมอ่านหน้าจออ่านออกเสียง

### 2.2 ส่วนที่ไม่รวม

- Seller Centre ที่ `/seller`
- Super Admin ที่ `/admin`
- สมัครร้านค้าที่ `/seller/register`
- Affiliate Hub ที่ `/affiliate`
- Creator Studio ที่ `/creator/studio` และ `/video/create`
- ชื่อร้าน ชื่อสินค้า รายละเอียดสินค้า ตัวเลือกสินค้า รีวิว คำบรรยายวิดีโอ ข้อความแชต และข้อมูลอื่นที่ร้านค้าหรือผู้ใช้กรอก
- การแปลอัตโนมัติและระบบจัดการคำแปลภายนอก
- การเปลี่ยนสกุลเงิน ประเทศปลายทาง ภาษี หรือเงื่อนไขทางธุรกิจตามภาษา
- การเปลี่ยนจากแอปหน้าเดียวไปเป็น SSR หรือระบบสร้างหน้าแบบสถิติล่วงหน้า

เส้นทางที่ไม่รวมยังใช้ URL เดิมแบบไม่มีรหัสภาษาและยังแสดงภาษาไทยในระยะแรก

## 3. หลักการด้านภาษาและเนื้อหา

1. หนึ่งหน้าจอใช้ภาษาของระบบเพียงภาษาเดียว ยกเว้นชื่อแบรนด์ เครื่องหมายการค้า ชื่อรุ่น ชื่อบุคคล และเนื้อหาที่ผู้ใช้สร้าง
2. คำศัพท์สำคัญต้องอ้างอิงอภิธานศัพท์กลาง เพื่อป้องกันการแปลคำเดียวกันหลายแบบ
3. ประโยคต้องเก็บเป็นหน่วยความหมายที่สมบูรณ์ ไม่ประกอบประโยคด้วยการต่อข้อความสั้นหลายส่วน เพราะลำดับคำของแต่ละภาษาไม่เหมือนกัน
4. ตัวเลข ราคา วันที่ เวลา และจำนวนรายการต้องจัดรูปแบบตามภาษา แต่สกุลเงินยังเป็นบาทและใช้เลขอารบิกทั้งสามภาษา
5. ข้อความจาก API ต้องส่งรหัสข้อผิดพลาดที่คงที่ให้หน้าเว็บแปลเอง ข้อความจากเซิร์ฟเวอร์ใช้เป็นข้อมูลสำรองและบันทึกวิเคราะห์ ไม่ใช้เป็นข้อความหลักเมื่อมีรหัสข้อผิดพลาด
6. ข้อมูลที่ผู้ใช้สร้างต้องแสดงตามต้นฉบับโดยไม่ติดป้ายว่าเป็นคำแปล

## 4. สถาปัตยกรรมการแปล

ใช้ `i18next` เป็นแกนกลางและ `react-i18next` สำหรับเชื่อมกับ React เนื่องจากรองรับการเปลี่ยนภาษา การแทนค่า การจัดการจำนวน และการแบ่งคำแปลเป็นหมวดโดยไม่ต้องสร้างกลไกเหล่านี้เอง

คำแปลเก็บในโครงการและแบ่ง namespace ตามหน้าที่:

```text
public/locales/
├── th/
│   ├── common.json
│   ├── navigation.json
│   ├── auth.json
│   ├── catalog.json
│   ├── commerce.json
│   ├── engagement.json
│   └── legal.json
├── en/
│   └── ...
└── my/
    └── ...
```

ความรับผิดชอบของแต่ละ namespace:

- `common`: ปุ่มทั่วไป สถานะ ข้อผิดพลาด การโหลด และข้อความที่ใช้ซ้ำ
- `navigation`: Navbar, Footer, Mobile Bottom Nav และเมนูภาษา
- `auth`: เข้าสู่ระบบ สมัครสมาชิก และบัญชีผู้ซื้อ
- `catalog`: หน้าแรก รายการสินค้า Mall ร้านค้า และรายละเอียดสินค้า
- `commerce`: ตะกร้า ชำระเงิน คำสั่งซื้อ รายการโปรด เปรียบเทียบ และติดตามพัสดุ
- `engagement`: ไลฟ์ วิดีโอ เกม คูปอง แชต และการแจ้งเตือน
- `legal`: ศูนย์ช่วยเหลือ ความเป็นส่วนตัว และข้อกำหนดการใช้งาน

ภาษาไทยเป็นต้นแบบของโครงสร้างคีย์ การทดสอบต้องเปรียบเทียบคีย์ของอังกฤษและพม่ากับภาษาไทยแบบลึกทุกระดับ คีย์ใช้ชื่อเชิงความหมาย เช่น `commerce.checkout.payment.cod` ไม่ใช้ประโยคภาษาไทยเป็นคีย์

ใช้ `useTranslation` ในคอมโพเนนต์ React และใช้ instance กลางเฉพาะโค้ดนอก React เช่นข้อความใน utility ไม่สร้าง helper แปลภาษาซ้ำซ้อนหลายชุด ส่วนข้อความ JSX ที่มีลิงก์หรือการเน้นข้อความภายในประโยคจึงใช้ `Trans`; ข้อความทั่วไปใช้ `t`

ไฟล์คำแปลโหลดตาม namespace ที่หน้าใช้งานผ่าน HTTP backend และใช้กลไก Suspense ที่มีอยู่แล้วในแอป ระหว่างโหลดต้องแสดงข้อความกำลังโหลดในภาษาปัจจุบันจาก namespace `common`

## 5. การจัดการภาษาและเส้นทาง

หน้าผู้ซื้อทุกหน้ามีรหัสภาษาเป็นส่วนแรกของ URL:

```text
/th
/th/shop
/en/shop
/my/shop
/th/product/:slugOrId
```

สร้าง utility กลางสำหรับ:

- ตรวจว่า locale รองรับหรือไม่
- แยก locale ออกจาก pathname
- เติม locale ให้ลิงก์ภายใน
- เปลี่ยน locale โดยคง pathname, query string และ hash เดิม
- สร้าง URL สำหรับ Canonical และ `hreflang`

สร้าง `LocaleBoundary` ครอบเส้นทางผู้ซื้อ ทำหน้าที่ตรวจ locale จาก URL ซิงค์กับ i18next อัปเดต `document.documentElement.lang` และบันทึกภาษาล่าสุดลง `localStorage`

กติกาการนำทาง:

- `/` ส่งต่อไปภาษาล่าสุดที่บันทึกไว้ และส่งไป `/th` เมื่อยังไม่เคยเลือกภาษา
- URL ผู้ซื้อเดิมที่ไม่มีรหัสภาษา เช่น `/shop` ส่งต่อไปเส้นทางภาษาไทย `/th/shop`
- URL ที่มีรหัสไม่รองรับ เช่น `/jp/shop` แสดงหน้าไม่พบเส้นทาง ไม่เดาภาษาแทนผู้ใช้
- การเลือกภาษาเปลี่ยนเฉพาะรหัสภาษา และต้องคงหน้า query string และ hash เดิม
- ปุ่มย้อนกลับและเดินหน้าของเบราว์เซอร์ต้องคืนภาษาตาม URL ในประวัติ
- ลิงก์จากหน้าไม่แปลภาษาไปหน้าผู้ซื้อใช้ภาษาไทยในระยะแรก
- ลิงก์ภายในหน้าผู้ซื้อใช้ locale ปัจจุบันเสมอ

เส้นทางผู้ดูแลและผู้ขายต้องประกาศก่อนเส้นทาง `/:locale` เพื่อไม่ให้ `seller` หรือ `admin` ถูกตีความเป็นรหัสภาษา

## 6. ตัวเลือกภาษา

เพิ่มตัวเลือกภาษาใน Navbar บนเดสก์ท็อปและในเมนูที่เข้าถึงได้บนมือถือ แสดงข้อความ `ไทย`, `English`, `မြန်မာ` โดยไม่ใช้ธงชาติ

ข้อกำหนด:

- ระบุภาษาปัจจุบันด้วยทั้งรูปแบบที่มองเห็นและ `aria-current`
- ใช้งานด้วยแป้นพิมพ์ได้
- ปิดเมนูเมื่อเลือกภาษา กด Escape หรือคลิกนอกเมนู
- หลังเปลี่ยนภาษา โฟกัสต้องอยู่ที่ปุ่มเลือกภาษา ไม่กระโดดไปต้นหน้า
- ไม่แสดงตัวเลือกภาษาบนเส้นทางที่ยังไม่รองรับหลายภาษา

## 7. SEO และข้อมูลกำกับหน้า

ทุกหน้าผู้ซื้อต้องอัปเดตข้อมูลต่อไปนี้ตาม locale:

- `<html lang="th|en|my">`
- `document.title`
- meta description และ keywords ที่จำเป็น
- Open Graph locale, title, description และ URL
- Twitter title และ description
- Canonical URL ที่มีรหัสภาษาปัจจุบัน
- `link[rel="alternate"][hreflang]` สำหรับ `th`, `en`, `my` และ `x-default`
- BreadcrumbList และข้อความใน JSON-LD

หน้าสินค้าใช้ชื่อและรายละเอียดสินค้าต้นฉบับใน structured data แต่ข้อความการตลาดและ breadcrumb ของระบบใช้ภาษาปัจจุบัน ฟังก์ชัน `slugify` ต้องรองรับอักษรไทย อังกฤษ พม่า ตัวเลข และเครื่องหมายที่ปลอดภัยต่อ URL โดย ID สินค้ายังคงเป็นตัวระบุหลัก จึงไม่พึ่ง slug ในการค้นข้อมูล

`x-default` ชี้ไป URL ภาษาไทย การเปลี่ยนภาษาไม่สร้าง Canonical ข้ามภาษา และต้องลบ alternate tags เก่าก่อนเขียนชุดใหม่เพื่อไม่ให้สะสมเมื่อผู้ใช้เปลี่ยนภาษาโดยไม่โหลดหน้าใหม่

ระบบปัจจุบันอัปเดตข้อมูล SEO ฝั่งไคลเอนต์ ระยะแรกจะรักษาสถาปัตยกรรมนี้ไว้ การทำ SSR หรือ prerender สำหรับประสิทธิภาพ SEO สูงสุดเป็นงานแยกในอนาคต

## 8. PWA และแบบอักษร

สร้าง manifest แยก 3 ไฟล์สำหรับ `th`, `en` และ `my` แล้วเปลี่ยน `link[rel="manifest"]` ตาม locale ชื่อแอป คำอธิบาย และทางลัดใน manifest ต้องตรงกับภาษา ส่วน `short_name` คงเป็น `Movemall`

เพิ่ม Noto Sans Myanmar เป็นแบบอักษรสำรองสำหรับอักษรพม่า โดยคงชุดแบบอักษรเดิมสำหรับไทยและอังกฤษ กำหนด line-height ที่รองรับสระและเครื่องหมายด้านบน/ล่างโดยไม่ถูกตัด และไม่กำหนดความสูงคงที่ให้กล่องข้อความสำคัญ

Service worker ต้องรวมไฟล์คำแปลและ manifest ที่จำเป็นในกลยุทธ์แคช โดยเมื่อไฟล์คำแปลโหลดไม่สำเร็จ แอปต้องใช้ภาษาไทยที่มีอยู่ในแคชหรือแสดงข้อผิดพลาดที่กู้คืนได้ ไม่แสดงคีย์ดิบแก่ผู้ใช้

## 9. การจัดการข้อผิดพลาดและภาษาสำรอง

- ถ้าคีย์อังกฤษหรือพม่าหาย ให้ใช้ข้อความไทยของคีย์เดียวกัน
- ถ้าคีย์ไทยหาย ให้แสดงข้อความทั่วไปที่ปลอดภัยและบันทึกชื่อคีย์ในโหมดพัฒนา ห้ามแสดงคีย์ดิบใน production
- ถ้าไฟล์ namespace โหลดไม่สำเร็จ ให้ลองใหม่หนึ่งครั้ง จากนั้นใช้ namespace ภาษาไทยที่แคชไว้
- ถ้า locale ใน URL ไม่รองรับ ให้แสดงหน้าไม่พบเส้นทางพร้อมลิงก์กลับ `/th`
- ถ้าข้อความ API ไม่มีรหัสข้อผิดพลาด ให้ใช้ข้อความทั่วไปตามภาษาปัจจุบันและบันทึกข้อความจริงสำหรับวิเคราะห์
- การเปลี่ยนภาษาระหว่างกรอกแบบฟอร์มต้องไม่ล้างค่าที่กรอก ตะกร้า หรือสถานะชำระเงิน

## 10. ลำดับการย้ายข้อความ

ดำเนินงานเป็นชุดย่อยที่สร้างและทดสอบได้อิสระ:

1. เพิ่มแกน i18n, locale utilities, `LocaleBoundary`, redirect URL เดิม และชุดทดสอบคีย์คำแปล
2. ย้ายส่วนกลางและเมนูเลือกภาษา เพื่อให้เปลี่ยนภาษาได้ครบทุกหน้าที่อยู่ในขอบเขต
3. ย้ายเส้นทางค้นพบสินค้า: หน้าแรก ร้านค้า Mall รายการสินค้า รายละเอียดสินค้า รายการร้านค้า และหน้าร้าน
4. ย้ายเส้นทางธุรกรรม: ตะกร้า ชำระเงิน ผลการสั่งซื้อ คำสั่งซื้อ รายการโปรด เปรียบเทียบ และติดตามพัสดุ
5. ย้ายบัญชีและการสื่อสาร: เข้าสู่ระบบ สมัครสมาชิก บัญชี แชต และการแจ้งเตือน
6. ย้ายความบันเทิง โปรโมชัน และเอกสารสาธารณะ
7. ปรับ SEO, PWA, service worker และแบบอักษรพม่า
8. ตรวจข้อความตกค้าง ความล้นของหน้าจอ การเข้าถึง และการทำงานครบทั้งสามภาษา

แต่ละชุดต้องผ่าน build และการทดสอบที่เกี่ยวข้องก่อนเริ่มชุดถัดไป ห้ามย้ายทุกหน้าในคอมมิตเดียว

## 11. การทดสอบและเกณฑ์ยอมรับ

### 11.1 การทดสอบอัตโนมัติ

- คีย์ในทุก namespace ของ `en` และ `my` ตรงกับ `th`
- ไม่มีค่าว่าง ค่า `null` หรือข้อความที่เป็นเพียงช่องว่าง
- locale utilities เติม แยก และเปลี่ยน locale โดยรักษา query string กับ hash
- redirect URL เดิมไปภาษาไทยถูกต้อง
- `LocaleBoundary` ซิงค์ URL, i18next, `html lang` และ localStorage
- ตัวเลือกภาษาคงหน้าปัจจุบันและสถานะแบบฟอร์ม
- SEO utility สร้าง Canonical และ alternate ครบโดยไม่ทิ้ง tag ซ้ำ
- ตัวจัดรูปแบบราคา วันที่ เวลา และจำนวนให้ผลลัพธ์ตาม locale ที่กำหนด
- API error code ถูกแปล และกรณีไม่มี code ใช้ข้อความทั่วไป

### 11.2 การตรวจข้อความ

- หน้าไทยไม่มีคำอังกฤษกำกับโดยไม่จำเป็น ยกเว้นข้อยกเว้นตามขอบเขต
- หน้าอังกฤษไม่มีข้อความระบบภาษาไทยหลงเหลือ
- หน้าพม่าไม่มีข้อความระบบภาษาไทยหรืออังกฤษหลงเหลือ
- ชื่อแบรนด์ ชื่อรุ่น และเนื้อหาที่ผู้ใช้สร้างไม่ถูกแปลโดยไม่ได้ตั้งใจ
- คำสำคัญสอดคล้องกับอภิธานศัพท์กลาง

### 11.3 การตรวจหน้าจอ

- ตรวจขนาดมือถือ 360, 390 และ 430 พิกเซล
- ตรวจเดสก์ท็อปอย่างน้อย 1280 และ 1440 พิกเซล
- ไม่มีข้อความล้น ปุ่มตัดคำ เมนูทับกัน หรืออักษรพม่าถูกตัด
- แป้นพิมพ์และโปรแกรมอ่านหน้าจอเข้าถึงตัวเลือกภาษาและการนำทางได้
- ตรวจเส้นทางสำคัญครบ: หน้าแรก → สินค้า → ตะกร้า → ชำระเงิน → ผลการสั่งซื้อ

### 11.4 คำสั่งตรวจโครงการ

- `npm run lint`
- `npm run build`
- `npm test`
- `npm --prefix server run build`

### 11.5 นิยามเสร็จสมบูรณ์

งานระยะแรกเสร็จเมื่อหน้าผู้ซื้อทั้งหมดในขอบเขตเปิดผ่าน URL ทั้งสามภาษาได้ เมนูสลับภาษาคงหน้าปัจจุบัน ข้อความระบบตรงกับภาษาที่เลือก ไม่มีคีย์ดิบหรือข้อความระบบผิดภาษาที่ทราบ การซื้อสินค้าหลักยังทำงานเหมือนเดิม และคำสั่งตรวจโครงการทั้งหมดผ่าน

## 12. ความเสี่ยงและวิธีลดความเสี่ยง

| ความเสี่ยง | วิธีลดความเสี่ยง |
|---|---|
| ข้อความกระจายอยู่ในคอมโพเนนต์จำนวนมาก | ย้ายทีละกลุ่มหน้าและเพิ่มตัวตรวจข้อความตกค้าง |
| ลิงก์เดิมขาด locale | ใช้ helper กลางและทดสอบ redirect/language preservation |
| ข้อความพม่ายาวหรือสูงกว่าพื้นที่เดิม | ตรวจ responsive layout และหลีกเลี่ยงความสูงคงที่ |
| คำแปลไม่ครบหรือไม่สม่ำเสมอ | ใช้ภาษาไทยเป็นต้นแบบ ตรวจคีย์อัตโนมัติ และใช้อภิธานศัพท์กลาง |
| ข้อความจาก API หลุดเป็นไทยในภาษาอื่น | เปลี่ยนจุดแสดงผลเป็น error code mapping ตามลำดับความสำคัญ |
| SEO tag สะสมเมื่อเปลี่ยนภาษา | ให้ SEO utility เป็นเจ้าของ tag และแทนที่ชุดเดิมทุกครั้ง |
| แคช PWA เก็บคำแปลเก่า | กำหนดเวอร์ชันแคชและทดสอบการอัปเกรด service worker |

## 13. งานระยะถัดไป

หลังระยะแรกมีเสถียรภาพ จึงออกแบบแยกสำหรับ Seller Centre, Super Admin, Affiliate, Creator Studio และข้อมูลหลายภาษาของสินค้า/ร้านค้า การเพิ่มข้อมูลสินค้าแบบหลายภาษาจะต้องเปลี่ยน schema, API, หน้าจอผู้ขาย การค้นหา และนโยบายคำแปล จึงไม่ควรปะปนกับงานส่วนติดต่อผู้ซื้อระยะแรก
